- Durability and damage rules for those files, so no crash leaves an unreadable state item standing in for a decision. Every write and every update is an atomic durable replacement: the module writes a sibling `*.tmp` in the same directory, fsyncs it, renames it over the target, and fsyncs the directory; an intent file is durable before the act it covers begins and is removed only after that act commits, with the directory fsynced after the removal. A progress record is never rewritten in place, so the last durable value is either the previous one or the new one and never a torn one. The sibling temp is the only other file the store contains; a stale `*.tmp` is ignored at start and removed. A file that fails to parse or is short is treated as uncleared, and for the two intent shapes identity is recovered from the filename, which carries module_id, generation and epoch, not from the body. Recovery then fails closed on what the body alone held. A damaged `mint_intent` body names no vault record, so no delete may be issued — deleting an unnamed record is impossible and guessing one is forbidden: the module leaves the damaged file untouched, re-mints the live generation at the next epoch under a fresh intent, and names the damaged file's path in its report and start-up log.
- Damaged `revocation_progress`, and where its steps' inputs come from. A damaged or short body is read as `highest_completed_step: 0`, and because the body's `user_jwt_id` and kick target are lost with it, recovery re-derives them rather than guessing: the participant record name is reconstructed from the filename identity through `cortexkit-bus-naming`'s participant grammar, and the module resolves that name through Claustrum's served record lookup for the `user_jwt_id` and the credential public key the kick addresses. Three outcomes, each with one action. The lookup returns the record: recovery replays from step (1), every step idempotent, so completed steps are no-ops and no restart path skips the claims update or the census delete. The lookup confirms absence: step (4) is the last step and deletes that record, so a confirmed absence proves the whole sequence committed — recovery clears the progress file and issues nothing. The lookup fails (refused, unreachable, timed out, unclassifiable): absence is neutral, so recovery defers, issues no step, retries once per sentinel period, and names the deferral in its report.
- Damage rules for the four fixed-name state items, whose filenames carry no identity to recover. A damaged `spawn_cursor.json` is read as absent, so the module snapshots and reconciles instead of resuming, which loses nothing. A damaged `sentinel_verdict.json` is read as absent, which is already this process's start state (down, class `Unavailable`, until its first probe answers). A damaged `self_mint_orphans.json` is left untouched with its path named in the report and start-up log, and further orphan names for that incarnation go to the report and log only; nothing is ever deleted from that list.
- Damaged `epoch_high_water.json` fails closed per generation rather than reconstructing. The high-water entry for a (module_id, generation) is written and fsynced before the mint intent that uses the epoch, so the recorded value is an upper bound on every epoch ever issued for it. Reconstruction from uncleared intent filenames and census maxima is not sufficient and is not used as a licence to continue: an epoch that was issued, cleared and then revoked — census entry deleted and vault record deleted — is remembered by no surviving source, so reconstructing a maximum from those sources could reissue it to a new holder under a recycled record name. A generation the daemon spawns afterwards has a fresh entry and is unaffected; the module never resets, zeroes or rewrites a damaged entry, and never treats a reconstructed maximum as authority to mint. Independently of the file, the module never overwrites a vault record: it resolves the record name by the served lookup immediately before every mint, treats a present record as proof that epoch was used, advances to the next epoch, retries, and names each collision in its report. Ownership of acts, so each slice has one writer to name, and one recovery rule so no crash leaves a usable orphan or a stranded identity.
- Credential minting: the module mints every per-process credential, its own, and the system-account user. Participant credentials use the foundation's per-process grammar `nats.{module_id}.g{generation}.e{epoch}`. Minting and writing the census key are one act. Before the vault mint the module writes the mint-intent record named above; it clears the record only after the census write commits.
- Root credentials first, on every start (chair ruling R9), and named so that a restart can find them. The module's own credential and the system-account user are the roots and are resolved before any census-decided recovery runs, because reading the census needs the very credential being recovered and, on a first boot, the bucket may not exist. The two root record names carry no generation and no epoch — `nats.ckbus.self` and `nats.sysaccount.{acct}` — precisely because they must be discoverable before any spawn generation is known; a restart under a new generation resolves the same two names the previous incarnation wrote, and no root name is derived from the per-process grammar. Both names are on slice 0's naming-constructor report list. On start the module resolves each root from Claustrum by the served record lookup — the `get` under that namespace, whose exact served spelling and reply shapes for present, confirmed-absent and error slice 0 records at fire time. If the record is present the module connects under it and only then runs census-decided recovery for every other intent, minting nothing and deleting nothing. If the lookup confirms absence the module mints that root under the bootstrap path with no census read, records that as the bootstrap event in its report and start-up log, and proceeds. If the lookup fails — refused, unreachable, timed out, or a reply the recorded shapes do not let the module classify — it concludes nothing: it mints nothing, deletes nothing, retries once per sentinel period, and answers health down with class `Unavailable` meanwhile. A crash between minting a root and its first successful connect needs no special case: the next start resolves the fixed name, finds it present, and uses it. Because the lookup is a served op today, this step carries no `ckcred-mint-unlanded`; the mint on confirmed absence does. Where a superseded own record exists that this rule cannot arbitrate, its name is appended to `self_mint_orphans.json` and named in the slice report and it is never deleted; deleting a named orphan needs the durable delete, so the bootstrap row carries `ckcred-delete-unlanded` as well as `ckcred-mint-unlanded`. Sweeping records never named this way would need Claustrum's audit-log read; this campaign does not do that sweep, and the residual is declared here rather than implied.
- Mint recovery for participant credentials is decided by the census, never assumed and never by an absent answer, and runs only after the root rule above has resolved the module's own credential. On restart, for each uncleared mint intent the module performs an authoritative census read: a snapshot on a live connection that either returns the entry for that module_id and generation or confirms its absence. If that read succeeds and an entry exists at exactly the intent's epoch naming the intent's vault record, the act committed before the crash: recovery clears the intent and deletes nothing. If that read succeeds and confirms absence or a mismatch, recovery is rollback — delete the vault record the intent names if it exists, never write or complete the census entry, then clear the intent — and this holds whether or not the intent's generation is still live; because rollback deletes a vault record, the arms that drive it carry `ckcred-delete-unlanded`. If the read does not succeed — broker unreachable, request timed out, or the read refused — recovery is deferred: the intent, the vault record and the census entry are left untouched, no destructive step runs, and the module retries once per sentinel period. A failed read is never proof that a mint did not commit. A live generation left without a census entry is re-minted by the ordinary reconciliation under a fresh epoch.
- Revocation: the four ordered steps in the foundation (claims update with `user_jwt_id`, census delete, `$SYS` kick, Claustrum record delete), in that order, with the observables the foundation names. The progress record is written and fsynced with `highest_completed_step: 0`, the `user_jwt_id` and the kick target before step (1), updated by atomic replacement to N immediately after step N commits, and cleared after step (4)'s update commits; 0 means no step has completed and 4 is the transient value between step (4) and the clear. On restart the module resumes at `highest_completed_step + 1`, reading a damaged or short record as 0 and re-deriving its inputs by the rule stated above. Reconciliation scans the census and cannot see a revocation that already deleted its census entry, so the progress record, not the census, is the recovery source for a half-done revocation. Step (4) is cleanup and is never mistaken for the revocation.
- Exactly once, defined so replay is testable. "Exactly once" counts effective state changes, not requests: the kick is delivered exactly once when the run's `$SYS` capture holds exactly one disconnect event for the target, and the vault record is deleted exactly once when the served lookup shows exactly one present-to-absent transition for that record name. Replayed requests are permitted and are required to be no-ops — a repeated delete of an already-absent record reports confirmed absence rather than erroring, and a repeated kick of an already-disconnected client emits no new disconnect event. Because Claustrum and the broker are outside this package, no slice assumes that behaviour: the arms assert it, a replay that errors instead of reporting absence fails the arm and is recorded in the slice report, and supplying that no-op delete is part of what discharges `ckcred-delete-unlanded`.

Standing rules carried from the foundation, restated because they are the ones a module implementer most often inverts.
- Absence is neutral: a watch with no snapshot, a dropped connection, a missing key, denies and grants nothing. A confirmed absence (snapshot on the current connection without the key, or an observed delete) is what the trait layer denies on locally, and server-side revocation is the enforcement that counts. Recovery obeys the same rule: an unsuccessful read is never a confirmed absence.
- The two counters are never one: spawn generation is SUBC's and the module never allocates it; credential epoch is the module's and starts at 0 per generation.
- Permission files are allow-only; wildcards are whole-token; every stream-bearing subject is emitted with the five literal stream names expanded per account.
- Inbox prefix is `_INBOX.{credential_public}` on every client the module runs, set before connecting.
- No constant taken from an unverified citation is hard-coded in an acceptance control; the supervisor's drain ceiling, the sentinel period and timeout, the claims-update and kick subject strings, and the JetStream request set are read at run time (from `supervisor.list`, from the module's start-up log line, or from A9's committed golden).
